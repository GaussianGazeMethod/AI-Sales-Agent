# 适配开发指南

## 1. 从下载到运行

1. 使用 Python 3.12 和 Node.js 20+，按根 README 安装后端/前端依赖。
2. 复制 `backend/.env.example` 为 `.env`，生成自己的 SECRET_KEY；不使用演示凭证处理真实数据。
3. 启动后端 8020 与前端 5230，先确认 `/health`、登录、列表及样例数据。
4. 填写自己的模型端点、模型名和密钥；重启后验证 `/api/v1/ai/status`，再用合成输入测试对话。
5. 先阅读需求、规则和完整场景，再修改对应实现。复制/克隆下载包后的目录作为独立项目，不依赖任何其他本机仓库。

## 2. 配置与需要改代码的边界

| 适配内容 | 入口 | 是否只改配置即可 |
|---|---|---|
| 应用名、CORS、数据库路径、上传目录、密钥 | `backend/.env` / `app/config.py` | 已有设置项可以 |
| 前端代理、端口 | `web/vite.config.ts`，MARKET_API_PROXY | 可以；同步 CORS |
| 模型供应商、模型名和参数 | `.env`、`backend/SETTINGS.yaml` | 兼容当前 provider 才可；仍需验证 |
| 业务行业、来源和机构类型 | `models/enums.py`、`core/dicts.py`、Schema、页面 | 需要同步修改代码与规则 |
| 销售阶段、硬门槛、概率 | `core/dicts.py`、`models/enums.py`、`sales_rules.py`、阶段服务 | 需要；不是改标题就完成 |
| AI 工作方法 | `spec/skills`、节点 Prompt、Schema、校验器 | 需要联合评审 |
| 角色和数据范围 | `core/deps.py`、`permissions.py`、菜单/路由 | 需要；菜单不授予权限 |
| 语音、IM、外部 CRM | 新接入模块复用 API/领域服务 | 需要实际实现 |
| 多实例与生产数据库 | `database.py`、调度、迁移及部署 | 需要重新设计与验证 |

可配置项完整列表见 [配置参考](配置参考.md)。默认阶段来自种子，仅首次空表初始化；修改默认列表不会覆盖已存在数据库中的标准。已有库要执行明确的数据迁移并保留历史证据。

## 3. 适配行业与业务规则

先为目标行业定义：客户与项目的区别、最小录入信息、有效意愿、阶段标准、采购路径、金额性质、工作日日历及角色范围。保持业务事实和计划分开，未知允许存在。

以“把学校客户改为企业客户”为例，不能只把页面中的学校改成公司：需检查 OrgType、四项规则、关键决策人标准、需求报告栏目、采购与签约证据、风险 Prompt、示例输入和数据种子。

## 4. 适配销售阶段

同步检查以下位置：

- `models/enums.py`：阶段代码；`core/dicts.py`：顺序、标签、默认标准、时长和权重。
- `models/stage.py`：证据、判断及流转持久化；`stage_service.py`：推进、回退与签约。
- `core/sales_rules.py`：固定双条件 ID、三态和组合规则。
- `assistant_stage_judge.py`、相关 Prompt/Schema：语义解释与返回结构。
- `stage_confirmation_service.py`、`assistant_projects.py`：人工采纳与聊天执行的一致性。
- 前端步骤、详情、标签、漏斗及筛选；完整案例和回归。

不得覆盖旧已达成证据来实现新标准。规则发布、数据迁移与重新评估需明确范围，不自动把历史事实重解释成新结果。

## 5. 线索验证的双入口

AI 入口在 `assistant_leads.py` 处理 pending/valid/invalid；表单跟进在 `followup_service.judge_validity` 仍使用二态。统一验证体验时必须明确怎样处理未回复、未知核实和“其他”动作，再同时修改领域逻辑、表单、Prompt、Schema 和回归。当前分发包没有把这种差异藏在配置里。

## 6. 适配模型与提示词

1. 保留 extract/dialogue/diagnose/compose 别名，使业务调用不绑定厂商模型名。
2. 在 Settings 和 YAML 中确认 API 兼容、流式响应、思考参数、温度、输出长度与超时。
3. 依次验证结构化输出、枚举、可空字段、引文和校验重试。
4. 用自己的典型消息、否定消息、歧义及对抗输入验证语义。
5. 最后验证记录与阶段副作用、幂等、失败恢复和页面回执。

只改 Prompt 不能绕过业务规则。新增输出字段要同步 Pydantic、宿主允许列表、数据库落点、序列化和前端类型。模型改成能返回文本不等于所有业务节点已兼容。

## 7. 修改 Skills 与规则资源

`business_skills.py` 会打包 Markdown 相对依赖；保留 `spec/skills`、`spec/doing` 及实际引用的 docs 文件。资源必须位于允许目录，不能引入隐藏配置或密钥。修改方法与规则产生新的内容修订，不伪造旧版本。

风险文本读取 `spec/doing/13-R1-R6风险判断基准.md` 并生成摘要。改变风险含义时同步实现和验证；旧风险保留其来源版本，不批量重判历史。

## 8. 接入其他系统

前端或外部应用先通过登录/API 授权。企业 IM/语音模块把外部身份映射为本系统用户，处理原始消息、幂等键和授权，再调用现有服务。不能把任意外部用户直接映射到 manager。

现有的 IM webhook、向量库配置或语音占位不代表实际通道已接通。新增通道需自行验证签名、重放、数据范围和错误回执。

## 9. 数据库与部署

SQLite 下有专用 PRAGMA、WAL 与补列逻辑。换数据库需替换这些逻辑并建立迁移链。多进程/多实例要确保定时任务不会重复回收、通知和生成周报；文件上传与 AI 状态存储也需共享设计。

Compose 使用本地端口与独立卷。更换访问域名同时检查代理、CORS、Token、上传目录、日志及备份。生产部署不在一键示例范围内。

## 10. 案例、测试和验证

`backend/examples/sales_cases.json` 是可编辑的合成案例源；`seed.py` 只预置展示数据，明确不等于模型回放。

```bash
cd backend
pip install -r requirements-dev.txt
pytest
```

回归使用独立临时数据库，不需要启动业务服务；模型替身只验证执行契约。真实模型、UI、报告导出和部署需单独验证。具体清单见 [43条业务用例](../spec/doing/24-AI助手TDD业务用例集.md)。

## 11. 已知边界

- 默认仅两个展示账号，无自助注册与用户管理页面；共用角色枚举不等于这些角色可登录使用。
- 默认数据包括阶段依据和签约结果，用于展示历史页面；这些依据明确为合成预置。
- 未提供语音识别、企业 IM、完整知识库和外部 CRM 的现成实现。
- 传统表单与 AI 的验证状态存在已说明差异；完整行业适配应评审它们。
- 报告一页需要实际渲染检查；模型计费和响应时间按实际供应商测量。
