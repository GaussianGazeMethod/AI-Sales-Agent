# 11 · UI 设计规范

## 1. 设计原则

让销售先完成工作，再按需展开依据。默认显示本次关键变化、阶段状态、下一步与时间；复杂来源、历史和规则通过展开查看。未知、计划、候选与真实成功分别显示。

## 2. 设计系统

颜色、字号、间距、圆角和阴影复用 `web/src/theme.ts` 与 `styles/app.css`。PC 使用 Ant Design，手机入口使用适合窄屏的对话布局。不要将 PC 表格按比例缩小到手机。

## 3. 导航与角色

一级分组为工作台、线索、客户、商机、AI、销售管理和个人中心；列表点入具体项目详情，不提供缺少项目 ID 的假详情菜单。菜单由 `router/menu.ts` 过滤，实际路由由 `router/index.tsx` 注册；后端仍负责权限。

## 4. 关键页面

| 页面 | 结构与重点 |
|---|---|
| 线索录入 | 最小资料先行、查重提示、缺项定位 |
| 线索列表 | 搜索/筛选、负责人和状态、跟进时效、进入记录 |
| 商机详情 | 客户/项目标题、阶段步骤、证据、跟进及下一步行动 |
| AI 对话 | 会话、项目上下文、消息与真实回执；需要时展开事实和报告 |
| 阶段候选 | 标准、原依据、拟采纳依据、可修正内容与显式确认 |
| 风险/管理 | 筛选、具体依据、状态处理和数据口径 |
| 手机文字入口 | 对话与项目摘要优先，复用同一账号与后端 |

## 5. 交互边界

- 写入成功只依据后端回执；处理中、失败、部分成功要可区分。
- 提交状态和防重复由前端配合，但幂等由后端保障。
- 不显示不可用的语音或企业 IM 功能按钮。
- 不把技术节点名、内部契约 JSON 或代码变量直接作为销售操作说明。
- AI 建议与销售行动分别标识，未采纳建议不能显示为已安排。
- 签约、金额更正和阶段采纳展示关键数据及来源，允许检查后确认。

## 6. 组件复用

`PageHeader`、`Guide`、`GateBanner`、`KpiCard`、`ProjectDossierDrawer`、`ProjectFacts`、`SalesActions`、`CompletedStandardReview` 与 `SignOpportunity` 复用同一设计语言。指标显示时间范围、分母和权限口径。

## 7. 可访问性与响应式检查

确保输入标签、键盘操作、焦点、禁用原因和颜色对比可理解。检查桌面宽屏、较窄 PC 和手机宽度的长客户名、长引文、未知金额、空列表、错误及加载状态。编译通过不能代替浏览器布局验证。

## 8. 适配时同步项

新增角色或页面需同步菜单、路由、页面请求和后端授权；修改阶段/来源显示需同步业务字典与证据结构。调整 UI 不应改变阶段、风险和资金含义。
