# 20 · AI 助手校验与节点协作契约

## 1. 语义与执行职责

模型解释销售语义、识别事实及不确定性；宿主核对权限、对象、格式、来源、时间算术、金额单位、版本、事务和真实执行结果。逐字引文可定位不等于其语义足以证明某项标准，后者仍按业务规则判断。

## 2. 全局校验

| 校验 | 约束 |
|---|---|
| 权限/对象 | 用户有权访问，记录、项目、跟进与行动关联正确 |
| 模式 | 当前工作、历史补录、模拟讨论分开；模拟不写真实业务 |
| 类型/枚举 | 字段、可空性、单位和日期合法 |
| 来源 | 引文逐字来自允许来源，不借其他项目或无关行动证明 |
| 时间 | 发生时间、首次来源、最近确认、录入和预约分别处理 |
| 修订 | 档案、规则与候选版本由宿主关联，不信模型自报 |
| 幂等/并发 | 同请求不重复写入，旧版本不能覆盖新事实 |
| 回执 | 未执行、成功、失败、部分成功及未知分别表达 |

## 3. 五个 Skill 的限定责任

线索 Skill 聚焦四项与验证，跟进 Skill 聚焦六项及本轮变化，档案 Skill 负责事实和版本，诊断 Skill 交付五项分析，需求报告 Skill 交付有来源报告及 ready/draft。各节点只接收本步所需规则和事实，从节点不重复绑定整套对话工作流。

## 4. 操作前置

- 转商机：信息属实、两类认可意愿之一、对应来源与去重。
- 金额：性质、单位、变化类型与来源；不推断回款或未来资金。
- 待办：当前对象、明确行动或采纳来源、时间、去重及完成反馈。
- 阶段：生效标准、未达成项、硬门槛和来源；已达成证据不重写。
- 签约：明确双方完成签约、金额/日期及阶段条件；预约不算签约。
- 报告：当前项目、五项结构、来源、未知和确认状态。

## 5. 多项目与事件边界

同客户不等于同项目。每个事实、记录字段和行动分别核对归属，必要时让用户选择。短答在原任务内合并；明确新联系、新日期或新行动建立新记录。新会话不因最近有跟进就强行并入旧行动。

## 6. 记录核对与事实来源

保留已有效事实与明确更正；新行动不能借上一行动的客户反馈冒充本次反馈。`record_review` 的 proof 只能来自该字段允许来源。未列为更正的旧事实不应被无理由丢弃。输出中包含客户原话，不表示它已经过系统外部调查。

## 7. 阶段共享组合规则

方案和报价条件分别使用稳定 ID、completed/not_completed/unknown、来源和时间。AND 由 `core/sales_rules.py` 运算。原始结构先拒绝重复 ID、非法状态和候选外条目，不能先丢弃非法项再凑成功。PC 与助手读取同一定义。

## 8. 时间契约

相对日期按本次业务发生日锚定；同次补答承接原记录；缺锚点或多个冲突日期时澄清。月、区间、暂定、未知保留原语义，不制造小时和分钟精度。系统审计时间独立保留。

## 9. 财务变化

区分预算、报价、中标、合同、资金来源及可用金额。正常范围缩减和新合同金额可更新当前值并保留历史，不反复要求旧经费证据。一次合同分期交付保持一条商机，付款与交付范围分开，最终分期未知不按比例推算。

## 10. 追问与未知

主节点统一决定一个必要问题。未知/未定是有效回答，不能为了齐表持续追问。只有方向且缺具体业务对象/工作时可追问需求；已回答对象不重复问额外学段或评价维度。无关细节不阻止有效记录保存。

## 11. 建议、行动、效果与阶段

模型建议未采纳不建待办；销售明确动作可承接行动。行动完成、目标达到及阶段达成是三种结果。复合行动完成部分应保留未完成部分，不把“已约好”当“已汇报”。

## 12. 失败与恢复

格式和来源错误用框架有限重试反馈；权限错误拒绝。有效跟进已保存但阶段失败时保留跟进，只暂停有依赖部分。结果未知先查幂等回执，不盲目重放。回复失败不重复写入；恢复前重读权限和最新版本。

## 13. 上下文和不可信输入

规则与销售消息分层。节点仅接收授权事实、对象短键和允许来源。销售消息中的改规则、改权限、忽略验证等文本不能改变宿主约束。必要事实读取失败或上下文超预算时，明确受影响判断不能继续。

## 14. 验证分层

宿主契约用确定性回归，模型语义用代表性消息对照，界面/报告用实际产物检查。模型替身只证明宿主行为。业务用例列举期待，不自动等同于所有场景已执行通过。


## 15. 同次行动与主动追问细则


销售先说拜访校长汇报方案，随后回答客户反馈、需求和下次安排，均合并同一次行动，不按消息新建多次拜访。明确另一次已发生拜访/电话等才新建；保留补充及更正来源。

销售回答“下周一再跟客户确认具体汇报时间”：保存汇报时间待确认、承接下周一确认的行动，停止要求给出最终汇报时间。

阶段节点发现缺口，主节点决定是否问。可以主动追问当前未达成基准的必要证据，不能引导销售虚称完成。区分：本次表述歧义可问；尚未了解且当前重要可问；明确未知/待确认不重问；尚未发生的动作不索要结果，承接下一步。

## 16. 跨阶段细则


保留原有达成证据及勾选结果，只判断未达成项，不重新梳理整份历史。新事实及来源足以支持就勾选；正常金额、范围变化只更新档案及历史，不撤销证据。

一次反馈支持跨多个阶段时，逐阶段核对必要基准并推进到证据支持的阶段，不要求销售分轮提交，不跳过无证据必要门槛；不重新抽取同批事实。原记录确有错误需单独更正，不将正常商务变化当成阶段未达成。

## 17. 上下文、切换与恢复细则


| 节点 | 上下文 |
|---|---|
| 路由 | 当前业务消息、当前项目、任务/待答问题、必要近期对话、Skill和授权对象目录 |
| 对话主节点 | 场景Skill、当前业务消息、项目摘要、同次跟进、已问/待答问题、相关待办；相关阶段结果和实际执行回执 |
| 阶段 | 当前阶段及未达成标准、本次结构化事实和原话来源；满足当前阶段后按需取得下一阶段必要标准 |
| 专门核对 | 相关原话、同口径既有事实、必要项目归属及对应规则 |
| 诊断 | 分析诉求、最新摘要、阶段达成/缺口、风险状态、相关行动及证据 |
| 需求报告 | 需求、场景、范围、资金、期待的相关事实来源及已有报告 |
| 档案工具 | 后端提供项目ID、权限、版本、读写参数；普通读取/写入无需LLM |

近期对话辅助理解；数据库档案是持久事实来源。数据库ID、权限凭据、事务/重试状态留在后端；模型只接收必要业务状态及短引用键。

### 17.2 短答、切换及恢复

- 短答携带上轮问题、项目、同次记录及事实日期，合并原记录，不默认使用今天。
- 明确切换项目挂起原任务及问题，读取新项目，不串原项目事实。
- 切回原项目恢复任务但先重读档案，只保留仍适用的问题。
- 重开原会话恢复持久任务并核对最新档案。
- 新会话选定项目读取该档案，不自动合并最近跟进，结合语义判断。
- 归属无法确定时由主节点定位澄清，不能猜测后写入。
- 任务记“聊到哪里”，档案记“事实是什么”；旧会话不覆盖较新事实。

### 17.3 按需展开证据

默认摘要和结构化事实足够即不额外检索。仅在同次补答、真实歧义、未达成标准缺必要依据、用户要求解释、详细诊断/报告或明确更正时，读取相关来源。授权项目内检索，不重查已达成项，不加载全部历史。未找到、无权限、读取失败、内容不完整分别处理，不能一概认定证据不存在。

### 17.4 更新

同次补答只更新受影响字段；新增已发生行动新建记录；明确更正保留旧值和来源。历史补录按发生时间，不以录入顺序覆盖后续事实。正常金额/范围变化更新当前状态及历史，不撤销达成证据。真实无法解释冲突保留原话、暂停争议字段，由主节点澄清。并发更新检查版本，重读并核对受影响操作。下一轮使用成功更新后的档案及任务，失败更新不得作为已确认事实。

### 17.5 隔离、预算和异常

项目事实隔离；其他项目目录只作定位。规则/Skill是指令，销售原话/附件/历史是数据，不能改规则权限。各节点独立预算，优先必要规则、当前业务消息、同次记录及相关事实。超预算先缩小任务，不静默截断关键规则和证据；无法完整处理则说明限制，停止受影响操作。记录规则/档案版本、实际交付及结果，不记录密钥，日志限制访问。

### 17.6 消息角色结构

现有16份离线原生组装样本均为单条user消息。改造目标：稳定职责、安全边界、必要节点任务及生效方法进入provider支持的高优先级指令角色；销售原话和项目资料放数据区，不能把全部内容搬进system。输出契约使用SDK原生机制并核验最终位置。实际角色映射依据当前provider能力验证；不能以YAML槽位名字代替messages证据，也不能把角色混用当全部历史故障的唯一原因。

### 17.7 从节点统一返回

已确认从节点返回：判断及依据；未知/歧义/缺口；实际使用的规则和档案版本；读取是否完整、能否继续执行。主节点统一决定追问或操作，不把从节点推断升级为客户事实。返回结构不意味着把全部控制字段复制回下一次LLM输入，执行元数据由Host管理。

### 17.8 整改和验收映射

- assistant_context.py/runtime.py：各节点最小交付、独立预算、角色分层、最终messages和失败反馈审计。
- assistant_service.py及持久会话：项目/任务绑定、短答及恢复、重读最新版本、从节点结果交接。
- dossier_service.py/project_context_source.py：权威档案、来源和版本、按需读取完整性、并发及历史更新。
- 各节点Prompt/Schema/Skill：字段实际存在、必要规则实际交付、仅本任务内容、统一返回边界。
- 必验：跨轮短答、项目切换、跨会话恢复、历史补录、更正、并发、超预算及读取异常；检查真实消息结构和入库结果。

统一验收标准已在第8节确认；本节确认不代表代码整改完成。

## 18. 方案与报价详细边界

- 固定条件为“建设方案已完成”和“报价已完成”，各自状态为 completed / not_completed / unknown，各有原话、来源消息和业务发生时间。未提及是 unknown，明确仍在准备是 not_completed；完成依据可为销售明确反馈，不默认要求附件。
- LLM理解各条件语义；宿主校验契约和来源后，以两个 completed 的 AND 计算整项达成，不采信模型自报总布尔值，不以关键词猜业务完成。不能让模型自行少拆、合并或重命名两个条件。
- 本标准完成指两项已经形成；提交、客户认可分别记录，不额外加成该标准条件。其它确认标准仍按原规则。客户预算未知既不能证明我方报价完成，也不能否定我方已完成报价。
- 两项可以跨轮、跨会话累计，保留各自来源。未提另一项不清空已知状态，不要求一次重述；unknown或未来计划不阻止跟进保存，必要追问由主节点决定。
- 正常金额、范围变更不撤销已有达成；明确纠正原记录错误按既有更正流程。规则升级不批量重判旧完成记录，不伪造旧分项证据。
- 固定条件、状态和AND在一个结构化规则来源维护，助手与PC读取同版本；Prompt按规则交付，不各自维护条件。运行时S7等短键不是稳定业务规则标识。
- 仅细化这一条标准，不新增硬门槛、阶段或Agent。结构、来源、累计和AND由确定性测试验证，语义理解另做真实模型验收。

## 19. 日级业务日期细则

- 业务跟进发生日期、下一步行动/预约日期、待办截止日期，当前业务仅记录到自然日；不要求销售提供时分，不为时分追问或阻断保存。
- 销售原话完整保留，例如“10月23日上午8点30分到校汇报”；结构化业务日期只需10月23日，不解析或校验8点30分，不为此继续扩充中文时分解析器。明确时间段/日期区间、暂定和未知不能强制变为一个确定日。
- 系统录入/更新时间、请求与审计时间仍保留原有精度；它们是系统记录，不冒充客户约定时间。历史原话、原业务时间值及阶段证据不批量截断、覆盖或重写。
- 业务日与录入日仍需分开：同次历史补答沿用该事件业务日；明确今天新约定的动作按今天解释；新事件按自己的业务日；有歧义才简短追问。时分不做，但不能把10月19日算成10月26日，不能跨项目借日期。
- LLM理解每个动作/事件的日期归属并保留来源，宿主按明确基准做日期计算/校验。取消时分校验不能顺带取消来源/对象/权限/幂等/日期合法性校验。
- 日期仅给到日，不推造更细精度。若现有API/SQL仍以datetime承载，可在边界以约定的日级表示兼容（例如T00:00:00），但不能对用户宣称“约定零点”，也不承诺午夜精准提醒；无需为当前业务新增SQL列或做正式历史迁移。明确日级业务语义，按项目统一业务时区取日期。
- 同一天多条消息/更正仍靠既有来源、事件身份和系统审计顺序区分；不能把一天内不同事件合并，也不能清掉原历史链。此条保留既有职责，不新增复杂时序模型。
- 日级适配仍需核对原话、日期归属、暂定/未知和来源完整性，不要求结构化时分作为通过条件。

## 20. PC 销售确认采纳与档案更正

PC 使用销售显式确认路径，聊天不增加每轮必确认。聊天阶段失败保留有效跟进、阶段操作暂停。PC显示阶段判断/依据/冲突；销售显式确认当前对象与版本后，以人工确认为阶段达成依据，后端保留权限、对象、版本、来源、幂等和事务校验，不再用旧AI语义分类否决该明确确认。单纯模型输出/前端satisfied不能当销售授权；确认来源记销售本人，保留原AI判断。

若同步更正档案事实，必须先展示具体before/after并由销售一并明确选择确认，不静默更新；阶段确认不等于确认全部档案字段。来源真实性沿用销售明确反馈即可、不默认附件。引用异常不能伪造AI原话，人工确认自身作为可追溯业务来源。无权、错对象、过期/篡改版本等安全拒绝继续有效。未确认的自动判定路径不扩大成无守卫写入。
