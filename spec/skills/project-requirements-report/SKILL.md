# 一页需求报告

## 职责与调用

这是辅助报告能力，由项目进度跟进调用，或由路由层响应用户明确的报告请求；不替代四个核心skill。

读取[统一交接契约](../shared/contract.md)。报告生成不等于档案已保存或阶段已推进。由项目档案服务保存报告版本及证据关联；跟进能力依据生效阶段基准提出阶段更新候选，由宿主校验执行。

## 事实输入

通过项目档案管理取得项目标识、最新需求事实及相关原文；结合本次销售文字或语音转写增量更新。不默认读取整个历史，不要求销售填写报告表单。

只使用客户反馈、销售明确提供的事实及有来源的资料。区分客户要求、客户期待、我方拟议方案及已确认建设范围。每个关键结论关联来源记录ID，必要时附短引文；没有材料不能捏造附件或客户确认。

缺失时返回影响方案的具体场景、问题和建设范围缺口，由主节点统一决定是否补问，由主节点每轮最多一个必要问题，默认销售协调资源，不问默认负责人。用户明确不知道或需要后续确认时标为待了解，不反复追问。

## 固定报告结构

标题为“客户／项目——需求报告”，注明事实截至日期、版本及确认状态。正文按以下五项组织，简洁结构化：

| 栏目 | 内容 |
|---|---|
| 建设背景与问题 | 为什么考虑建设，当前业务痛点；未明确则说明 |
| 核心需求与场景 | 服务对象、具体业务场景、已有标准或系统、客户关注的能力 |
| 建设范围与约束 | 已确认范围、分期及系统对接要求；区分客户要求与我方建议，未决范围单列 |
| 资金与客户期待 | 客户提供的资金来源及本项目金额/预算区间；合同验收要求与标杆等运营期待分别注明 |
| 待确认与下一步 | 当前重要缺口及已明确行动、时间；不重复现有事实，不编造截止日期 |

需求报告不是解决方案或诊断报告：不展开技术架构，不新增未采纳行动，不生成无依据的风险、产品承诺或成功指标。金额必须注明报价、预算或合同等性质，不拿报价替代客户预算。

## 可用性与阶段材料

报告能力同时返回可用性及真实缺口：需求依据足以说明服务对象和具体业务工作时为ready；通用业务对象类别和工作名称已足够，不强制学段、数量、细分流程或实施指标；只有产品方向、认可或标杆期待，尚不能理解服务对象与实际工作时为draft。草稿可以保存、展示及继续补充，不能因为正文有五栏就作为阶段达成材料。预算、详细技术实现或部分建设约束未知不单独使已有具体需求退回草稿。诊断能力不负责此判断。

可用性由本能力理解事实后判断；程序只校验返回结构、来源并按状态执行，不用关键词判断需求成熟度。缺口交给主节点统一决定是否追问，避免为了所有字段完整而追问。与报告正文保持一致，不能一边写核心对象待确认，一边称需求已充分。

## 预算与阶段边界

第二环节允许以AI整理、有原始事实依据的需求报告作为报告，不强制另传独立文件。预算未知标“待了解”，不因预算未知单独阻止进入方案报价；进入方案报价后按 [R1–R6规则](../../doing/13-R1-R6风险判断基准.md) 提醒资金来源或预算范围缺口。

这属于第二环节基准修订，七环节顺序不变；第四环节经费确认仍需满足其已确认条件。本skill不因报告已生成就宣称需求已获客户确认、阶段全部达成或资金落实。若运行系统仍使用旧规则，按统一契约报告规则版本不符，不绕过校验。

## 一页原则与渐进展开

正文以约600–800个中文字符为编辑目标；A4、常规页边距、正文11–12磅，标题及简短来源标注计入一页，不缩小字体挤内容。字数不保证分页：实际导出Word时使用可用文档工具生成并渲染检查，超页先删重复、压缩历史，再检查；无法渲染时明确未验证一页。

默认展示五项简洁报告；详细依据通过链接展开到原始跟进及附件，不额外附长篇报告规避一页限制。关键缺口即使字数紧张也保留，不为排版删掉金额性质、未知状态或关键约束。

## 版本、交接与回复

向档案能力交接报告正文、项目ID、事实截至时间、来源记录ID、待确认项及变更摘要。事实发生时间与报告生成时间分开；历史补录不让旧报告覆盖当前版本。依据变化生成新版本，保留旧版本。

报告状态区分“AI整理、待核对”“销售已核对”“客户已确认”；只有对应明确反馈才能更新状态，禁止AI自认客户确认。没有宿主保存回执时返回拟报告，不假称已归档。

场景讨论不写业务数据。收尾只说明报告生成/更新结果及最关键待确认项，不再复述整份档案。
